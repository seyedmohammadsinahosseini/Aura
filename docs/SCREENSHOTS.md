# Screenshots and how to capture your own

## What is in `docs/images/` and what each file is

| File | Kind | Truthful description |
|------|------|----------------------|
| `architecture.png` | **Generated diagram** | Rendered from the sources in this repository: the camera → hub → orchestrator → pipeline → storage/API path with the FFI seam and the module-registry gate. The editable form is the Mermaid block in [ARCHITECTURE.md](ARCHITECTURE.md) / [README.md](../README.md#architecture-at-a-glance). |
| `pipeline.png` | **Generated diagram** | Per-frame stage sequence with the gates and the two branches (recognise vs. queue-for-review). |
| `erd.png` | **Generated diagram** | SQLite tables and their relations, drawn from the `CREATE TABLE` statements in `services/storage/FaceDatabase.cpp`. |
| `detection-overlay.png` | **Illustrative rendering** | A synthetic frame produced by `docs/images/render_detection_overlay.py`, drawing boxes/IDs in the style of `DetectionDrawer` / `RecognitionDrawer`. **It is not a capture of a real camera and contains no real faces.** |
| `dashboard-concept.png` | **Concept mockup** | A design sketch of the operator UI that consumes this API. It is **not** a screenshot of shipped software — this repository contains no frontend. Watermarked to say so. |

Anything else that ever appears in this folder must be labelled by its caption; the README keeps the
same distinction. I would rather show four honest diagrams than one impressive fake.

## Capturing real output from your hardware

`scripts/capture_screenshots.sh` grabs what the running backend can actually give you — live preview
frames, redacted camera/person/attendance JSON, and the dashboard stats — into
`docs/images/captures/`:

```bash
./build/faceauth &                                  # or: ./build/faceauth-admin
./scripts/capture_screenshots.sh http://localhost:8080 docs/images/captures
```

It writes one JPEG per camera from `GET /api/cameras/{uid}/stream`, plus pretty-printed JSON for
`/api/dashboard/stats`, `/api/persons`, `/api/cameras` and `/api/attendance/summary`, and a text
`console.txt` with the version banner, `curl -sI` on the health endpoint and the DB table list. It
refuses to capture crops/unknown-face images by default so you cannot accidentally commit biometric
data; `--with-crops` is opt-in and prints a warning about what you are about to put in git.

Useful one-liners for the same job:

```bash
# the annotated live view (the drawer overlay is composited server-side)
ffmpeg -y -i "http://localhost:8080/api/cameras/1/stream" -frames:v 1 docs/images/captures/live-01.jpg

# the API as a reviewer will type it
curl -s localhost:8080/api/dashboard/stats | python3 -m json.tool > docs/images/captures/stats.json

# the terminal output, if you want a screenshot of the daemon's own log
tmux capture-pane -p -S -40 > docs/images/captures/console.txt
```

For a cropped terminal image, `convert -crop` (ImageMagick) or `shutter`/`gnome-screenshot` work;
save as PNG (text renders better losslessly) and keep the file under ~400 KB so the repository stays
fast to clone.

## Rules this repository follows

1. **Never commit real faces.** Face crops are the most sensitive artifact the system produces; the
   `.gitignore` blocks `*.jpg`/`*.png` outside `docs/images/`, and CI
   (`scripts/check_repo_hygiene.py`) fails if a crop or database file appears anywhere.
2. **Label illustrative images as illustrative.** See the table above; captions in the README repeat it.
3. **Show the API as it behaves.** Screenshots of `curl` output are worth more than a mockup, because
   they are checkable — `docs/API.md` documents the same payloads.
4. **Keep images small and reproducible.** Diagrams are generated by the scripts in `docs/images/`, so
   a reviewer can regenerate them from the code instead of trusting a picture.

## Regenerating the diagrams

```bash
python3 docs/images/render_diagrams.py        # architecture.png, pipeline.png, erd.png
python3 docs/images/render_detection_overlay.py  # detection-overlay.png
```

Both scripts read the source tree where possible (the diagram nodes are derived from the directory
names and the tables from the `CREATE TABLE` statements), so they do not drift as the code moves.
